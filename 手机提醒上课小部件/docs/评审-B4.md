## 阻塞项（3 条）

| # | 级别 | 问题 | 位置 |
|---|---|---|---|
| 1 | HIGH | 2×2 深链在应用存活时点击失效：MainActivity 未处理 onNewIntent，`timetable://courseEdit` 深链仅在冷启时生效 | `MainActivity.kt`、`app/src/main/AndroidManifest.xml:19-20` |
| 2 | MEDIUM | 双装配并存：`ReminderGraph.cached` 从未被生产路径注册，闹钟触发/开机时自建第三套 Repository+scheduler，其 mutex 与写钩子链路的 scheduler 不共享，串行化承诺失效 | `ServiceLocator.kt:81-94`、`ReminderGraph.kt:25-28` |
| 3 | MEDIUM | §8.2 首页提示条缺「精确闹钟未授权」分支，设计要求三条件按优先级只显一条，实现仅两条 | `HomeScreen.kt:121-137` |

### 阻塞项 1（HIGH）——深链 onNewIntent 无人处理

`WidgetClickAction.onAction` 用显式 Intent（ACTION_VIEW + data + `setClassName`）拉起 MainActivity。冷启时 `NavController.onGraphCreated` 会读一次 `activity.intent` 完成 `handleDeepLink`（已反编译 navigation-compose 2.8.5 / navigation-runtime 2.8.5 验证：NavHost 与 rememberNavController 均不引用 Intent、不注册 onNewIntent 监听；唯一分发点在 `setGraph → onGraphCreated`，且有 `deepLinkHandled` 一次性标志）。但 MainActivity `launchMode="singleTask"`，**应用已存活时系统只回调 `onNewIntent`，而 MainActivity 没有任何覆写**（全工程 grep 无 onNewIntent/handleDeepLink）——桌面点击小组件只会把 App 带回前台停留在原页面，§7.1「点击 → 打开该课程详情页」在最常见的后台存活场景下确定性失效。Manifest 注释「onNewIntent 交给 NavHost 处理」与库实际行为不符。

**建议修法**：MainActivity 覆写 `onNewIntent`（或用 `addOnNewIntentListener`），调用 `navController.handleDeepLink(intent)`；需将 NavHostController 从 `TimetableApp` 上提至 MainActivity 持有（或经 CompositionLocal/回调传入）。同时修正 manifest 注释。

### 阻塞项 2（MEDIUM）——ReminderGraph.cached 与 ServiceLocator 双装配

`ServiceLocator.init` 经 `buildGraph` 构建了自己的 Repository（钩子链：重排→Worker→小组件刷新）与 scheduler S1，但**从不注册进 `ReminderGraph.cached`**。闹钟/开机广播把进程带起时（即使 App 常驻、进程温热），`cached==null` → `buildProductionRepository` 再建一套文件库 Room 实例 + scheduler S2，且其 ChangeNotifier **缺 `WidgetUpdater.refreshAll` 环节**，与 app 路径钩子链不一致。后果：

1. `ReminderSchedulerImpl.kt:22`「并发由 mutex 串行化」不成立——S1（写钩子）与 S2（闹钟触发）各持 mutex，可并发执行 cancel-then-set；最坏交错（S2 读到旧课程数据、后写码集覆盖 S1）会复活已删除/已移动课程的陈旧闹钟，直到下一次变更或 04:00 Worker 才纠正。
2. 单进程最多三个 Room 实例（ServiceLocator、cached 兜底、WidgetGraph），资源浪费且装配语义漂移。

**建议修法**：给 `ReminderGraph` 增加 `register(graph)` 入口（或在 `cached` 里允许外部注入已建 graph），ServiceLocator.init 构建后注册，保证全进程单例；冷启兜底链路钩子链与 app 路径对齐。

### 阻塞项 3（MEDIUM）——首页缺精确闹钟提示条

§8.2：「顶部条件提示条：通知权限未授 / 精确闹钟未授权 / 学期未设置（三者按优先级同时只显示一条）」。`HomeScreen` 的 `when` 仅实现学期未设置与 notifDenied 两支。修法：在横幅条件链中补 `Build.VERSION.SDK_INT >= 31 && !alarmManager.canScheduleExactAlarms()` 一支，动作跳设置页既有「去开启精确闹钟」逻辑。

## 其余发现（非阻塞）

- **LOW** — 通知文案取自排程时的 extras：课程改名/换教室后触发的在途闹钟仍播旧 title/body（`AlarmReceiver.kt:44-52` 重查仅校验存在/停课/提醒开关，未重造文案）。§6.1 只要求防陈旧跳过，属设计内行为，记录备查。
- **LOW** — POST_NOTIFICATIONS 被「不再询问」拒绝后，首页「去开启」再次 `launch()` 静默无效，未引导跳 `ACTION_APP_NOTIFICATION_SETTINGS`；且 `notifDenied` 仅 `rememberSaveable`，进程重启后每次冷启会自动再弹系统授权框（§6.2 语义为「首次进入首页时请求」）。
- **LOW** — 重启后午夜日切 Alarm 不重建：BootReceiver 只走 `rescheduleAll`，`MidnightAlarm.schedule` 不在 BOOT 链路；日切精度降级为由 15min Worker 兜底（≤15 分钟误差），建议 BootReceiver 顺带重设。
- **LOW** — 设置页 `exactOk` 在 composition 中一次性读取（`SettingsScreen.kt:270-273`），从系统设置返回后不随 onResume 刷新，需重进页面才更新；可挂 `Lifecycle.Event.ON_RESUME` 观察或以 key 重算。
- **INFO** — Receiver 协程健壮性：`AlarmReceiver`/`BootReceiver`/`MidnightAlarmReceiver`/`TimeChangeReceiver` 均为 `CoroutineScope(Dispatchers.X).launch { ... } finally { finish() }` 模式，无 try/catch——DB/AlarmManager/Glance 任一异常将沿默认处理器崩溃进程（`finally` 仅保证 `pendingResult.finish()`）。建议包一层 catch 静默降级（本轮未计阻塞，正常路径不触发）。
- **INFO** — 渠道创建时机与设计措辞差异：§6.1 说「Application.onCreate 建立」，实现改为 `NotificationHelper.ensureChannel` 首用前幂等创建（无自定义 Application 类），额外覆盖了 Receiver 冷启路径，语义等效，总控验收知悉即可。
- **INFO** — 通知 id 用 `courseId.toInt()`：同课不同时刻复用同一通知 id，后发覆盖先发；§6.3「同课同时刻只发一次」由 requestCode 去重保证，通知 id 仅影响覆盖行为，可接受。
